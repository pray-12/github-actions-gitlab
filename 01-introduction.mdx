# GitHub Actions — Introduction

## 1. What is GitHub Actions?

**Answer:**

GitHub Actions is a CI/CD automation platform integrated into GitHub.

It allows us to automatically **build, test, scan, package, and deploy** applications when something happens in the repository, such as a code push or pull request.

For example:

```text
Developer pushes code
        ↓
GitHub Actions starts
        ↓
Build
        ↓
Test
        ↓
Security Scan
        ↓
Docker Build
        ↓
Push Image to ECR
        ↓
Deploy
```

So, instead of manually performing these tasks, GitHub Actions automates them.

---

## 2. What is a workflow in GitHub Actions?

**Answer:**

A **workflow** is an automated CI/CD process defined in a YAML file.

Workflow files are stored inside:

```text
.github/workflows/
```

For example:

```text
.github/
└── workflows/
    └── ci.yml
```

A workflow defines:

* When the pipeline should run
* What jobs should execute
* Which machine should execute the jobs
* What steps should be performed

Think of a workflow as the **complete CI/CD pipeline**.

```text
Workflow
   │
   ├── Trigger
   │
   └── Jobs
        │
        ├── Build
        ├── Test
        └── Deploy
```

---

## 3. What are the main components of a GitHub Actions workflow?

**Answer:**

The important components are:

```text
Workflow
 ├── name
 ├── on
 └── jobs
      ├── runs-on
      └── steps
           ├── uses
           └── run
```

You can remember them like this:

| Component | Meaning                         |
| --------- | ------------------------------- |
| `name`    | Name of the workflow            |
| `on`      | When the workflow runs          |
| `jobs`    | Work that needs to be performed |
| `runs-on` | Machine where the job runs      |
| `steps`   | Individual tasks inside a job   |
| `uses`    | Uses a reusable action          |
| `run`     | Executes a shell command        |

---

## 4. What is the `name` field?

**Answer:**

`name` defines the name of the workflow.

Example:

```yaml
name: Java CI
```

This name appears in the GitHub Actions UI.

It does not control how the pipeline works. It is mainly used to identify the workflow.

---

## 5. What is the `on` keyword?

**Answer:**

`on` defines **when the workflow should start**.

For example:

```yaml
on:
  push:
```

This means:

> Run the workflow whenever code is pushed to the repository.

Another example:

```yaml
on:
  pull_request:
```

This runs the workflow when a pull request event occurs.

Common triggers are:

```text
push
pull_request
workflow_dispatch
schedule
release
```

So remember:

```text
on = When should my pipeline start?
```

---

## 6. What is a job in GitHub Actions?

**Answer:**

A **job** is a collection of steps that are executed together on a runner.

For example:

```yaml
jobs:
  build:
    runs-on: ubuntu-latest

    steps:
      - run: mvn clean package
      - run: mvn test
```

Here:

```text
Job: build
   │
   ├── Build application
   └── Run tests
```

A workflow can contain multiple jobs.

For example:

```text
Workflow
   │
   ├── Build Job
   ├── Test Job
   └── Deploy Job
```

---

## 7. What is a step?

**Answer:**

A **step** is an individual task inside a job.

For example:

```yaml
steps:
  - run: mvn clean package
  - run: mvn test
```

There are two steps here:

```text
Step 1 → Build application
Step 2 → Run tests
```

Steps inside the same job normally execute **sequentially**.

So:

```text
Job
 │
 ├── Step 1
 │
 ├── Step 2
 │
 └── Step 3
```

---

## 8. What is a runner?

**Answer:**

A **runner is the machine that executes a job**.

For example:

```yaml
runs-on: ubuntu-latest
```

GitHub provides a machine for the job and executes the steps on it.

For example:

```text
GitHub Actions
      ↓
Ubuntu Runner
      ↓
Checkout Code
      ↓
Build
      ↓
Test
```

Common GitHub-hosted runners include:

```yaml
runs-on: ubuntu-latest
```

```yaml
runs-on: windows-latest
```

```yaml
runs-on: macos-latest
```

You can also use your own machine using:

```yaml
runs-on: self-hosted
```

---

## 9. What is the difference between a GitHub-hosted runner and a self-hosted runner?

**Answer:**

### GitHub-hosted runner

GitHub provides and manages the machine.

```yaml
runs-on: ubuntu-latest
```

You don't have to maintain the operating system or runner machine.

### Self-hosted runner

You provide and manage the machine.

```yaml
runs-on: self-hosted
```

The machine could be an:

```text
EC2 instance
On-premise server
Virtual machine
Physical server
```

Simple way to remember:

```text
GitHub-hosted → GitHub manages the machine

Self-hosted → We manage the machine
```

---

## 10. What is an action in GitHub Actions?

**Answer:**

An **action is a reusable piece of automation**.

Instead of writing all the commands ourselves, we can use an existing action.

For example:

```yaml
- uses: actions/checkout@v4
```

This action checks out our repository code onto the runner.

Another example:

```yaml
- uses: actions/setup-java@v4
```

This action sets up Java on the runner.

So:

```text
Action = Reusable automation
```

---

## 11. What is the difference between `uses` and `run`?

**Answer:**

`uses` uses an existing reusable action.

```yaml
- uses: actions/checkout@v4
```

`run` executes a command directly on the runner.

```yaml
- run: mvn clean package
```

Think of it as:

```text
uses → Use something that already exists

run  → Execute my own command
```

Example:

```yaml
steps:

  - uses: actions/checkout@v4

  - run: mvn clean package
```

Here:

```text
checkout → uses an action
Maven    → runs a command
```

---

## 12. Why do we use `actions/checkout`?

**Answer:**

The runner needs our source code before it can build or test the application.

We use:

```yaml
- uses: actions/checkout@v4
```

to check out the repository code onto the runner.

The flow is:

```text
GitHub Repository
       ↓
actions/checkout
       ↓
Code available on Runner
       ↓
Build / Test / Scan
```

Without checking out the code, commands such as:

```bash
mvn clean package
```

would not have the application source code to work with.

---

## 13. Can one workflow have multiple jobs?

**Answer:**

Yes.

For example:

```yaml
jobs:

  build:
    runs-on: ubuntu-latest
    steps:
      - run: mvn clean package

  test:
    runs-on: ubuntu-latest
    steps:
      - run: mvn test

  deploy:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Deploy"
```

The workflow contains three jobs:

```text
Workflow
   │
   ├── Build
   ├── Test
   └── Deploy
```

---

## 14. Do multiple jobs run sequentially by default?

**Answer:**

No.

If there is no dependency between jobs, GitHub Actions can run them **in parallel**.

For example:

```text
        ┌── Build
Workflow┤
        ├── Test
        └── Deploy
```

If we want one job to wait for another, we use `needs`.

---

## 15. How do you make jobs run sequentially?

**Answer:**

Use the `needs` keyword.

Example:

```yaml
jobs:

  build:
    runs-on: ubuntu-latest
    steps:
      - run: mvn clean package

  test:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - run: mvn test

  deploy:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - run: echo "Deploy"
```

Now the flow is:

```text
Build
  ↓
Test
  ↓
Deploy
```

`needs` means:

> This job depends on another job completing successfully.

---

## 16. What happens when a step fails?

**Answer:**

By default, if a step fails, the remaining steps in that job are not executed.

Example:

```yaml
steps:

  - run: echo "Step 1"

  - run: exit 1

  - run: echo "Step 3"
```

Result:

```text
Step 1        ✅
Step 2        ❌
Step 3        ⏭️ Skipped
```

The job is marked as failed.

Failure handling can be customized using conditions such as:

```yaml
if: always()
```

We will cover conditions separately.

## 17. What is the difference between a workflow, job, step, runner and action?

**Answer:**

This is one of the most important things to understand.

Think about a CI/CD pipeline like this:

```text
WORKFLOW
│
├── JOB
│    │
│    ├── STEP
│    ├── STEP
│    └── STEP
│
└── JOB
     │
     ├── STEP
     └── STEP
```

The **runner** is the machine where each job executes.

An **action** is something a step can use to perform reusable work.

### Easy way to remember:

```text
Workflow → Complete pipeline

Job      → Group of tasks

Step     → Individual task

Runner   → Machine executing the job

Action   → Reusable automation
```

## 18. Can you explain a GitHub Actions workflow from beginning to end?

**Answer:**

Yes.

For example:

```yaml
name: Java CI

on:
  push:
    branches:
      - main

jobs:

  build:

    runs-on: ubuntu-latest

    steps:

      - name: Checkout Code
        uses: actions/checkout@v4

      - name: Setup Java
        uses: actions/setup-java@v4
        with:
          java-version: '17'
          distribution: 'temurin'

      - name: Build Application
        run: mvn clean package

      - name: Run Tests
        run: mvn test
```

The execution flow is:

```text
Developer pushes code
        ↓
push trigger detects it
        ↓
Workflow starts
        ↓
GitHub provides Ubuntu runner
        ↓
Checkout repository
        ↓
Setup Java
        ↓
Build application
        ↓
Run tests
```

So when explaining it in an interview, you can say:

> "I define my CI/CD process in a YAML workflow under `.github/workflows`. The `on` section defines when the workflow runs. Inside `jobs`, I define the work that needs to be performed. Each job runs on a runner, and each job contains multiple steps. I use `uses` for reusable GitHub Actions and `run` for executing shell commands."

---

## 19. What is the basic structure you should remember?

**Answer:**

You don't need to memorize the entire YAML.

Just remember this structure:

```yaml
name: CI Pipeline

on:
  push:

jobs:

  build:
    runs-on: ubuntu-latest

    steps:

      - uses: actions/checkout@v4

      - run: mvn clean package
```

Then remember:

```text
name
 ↓
When? → on
 ↓
What work? → jobs
 ↓
Where? → runs-on
 ↓
What tasks? → steps
 ↓
Reusable action? → uses
 ↓
Command? → run
```

That's the core of GitHub Actions.
